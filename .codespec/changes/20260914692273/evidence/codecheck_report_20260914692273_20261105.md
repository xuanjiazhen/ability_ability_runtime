## 2. 必须立即处理（P1）

### F-01 同任务同 pid 重复纳管 → 注销一次即静默解除管控（引用计数错配）

- **证据链**【代码】：
  1. task_mgr 注册无 (taskId,pid) 去重，仅 1000 上限 — `services/appmgr/src/task_mgr/task_manager_service.cpp:418`（`attributions.size() >= TASK_MAX_ATTRIBUTIONS_PER_TASK` 前无 pid 查重）
  2. 重复注册可达 — dump 调试钩子 `DumpRegisterManagedProcess`（task_manager_service.cpp:450）直接调 `RegisterManagedProcess`，无任何去重
  3. schedule 侧第二次 add 被守卫丢弃 — `services/appmgr/src/process_schedule/process_schedule.cpp:56-59`（`attribution already tracked ... return`），taskLevels 保持 1 条
  4. 每次注销都触发移除 — `UnregisterManagedProcessInner`（接线）→ `OnAttributionRemoved(taskId, removedPid)`；`RemoveAttributionLocked`（process_schedule.cpp:148）无条件 `taskLevels.erase(taskId)`
- **触发路径**：register(taskId,P) ×2 → unregister 其中 1 条 → task_mgr 仍持 1 条归因（dump 可见），schedule 已移除该 (task,P) 归属与豁免 → 进程实际仍被任务纳管但 effectiveLevel 丢失、豁免提前释放。
- **后果**：INV-2（effectiveLevel==max）与 INV-3（豁免无泄漏）违例；AC-6.1 可观察行为被破坏（管控静默消失，方向为欠管控，非越权）。
- **Refute 记录**：反例"真实纳管通道可能上层去重"不成立（通道未交付且 dump 钩子今天可达）；反例"重复注册无业务意义"不成立（设计载荷即多工具类型同 pid 共管）。
- **修复方向**（用户确认后另起任务）：schedule 增加 (taskId,pid) 引用计数（add 递增/ remove 递减/ 归零移除），或 task_mgr 注册时按 (taskId,pid) 去重。前者更贴合"幂等键 taskId+pid+类型"设计。

## 3. 建议跟进（P2/P3）

### F-02（P2）负载跳变 → 全量重判路径无服务层单测
- **证据**【代码】：`TaskManagerService::OnSystemLoadLevelChanged`（task_manager_service.cpp）无任何测试调用（grep 全 test/ 仅 judge 层缓存测试命中）。
- **影响**：AC-6.7 的负载触发分支（VM-3 场景 5/6）与"重判全部任务"路径仅编译验证。风险：该路径回归无网。
- **修复方向**：service 层补 1 用例：load 4→5 触发后台任务 MEDIUM→LOW 且 process_schedule effectiveLevel 跟随（复用现有 fixture）。

### F-03（P2）前台 Ability 计数在 FG→TERMINATED 路径泄漏
- **证据**【代码】：`task_schedule_observer.h` 仅处理 `ABILITY_STATE_FOREGROUND/BACKGROUND`，`TERMINATED/END` 被忽略（grep 0 命中）。
- **前提**：进程异常消亡时 Ability 可能不经 BACKGROUND 直接 TERMINATED（此处为推测，需 AbilityMS 生命周期数据确认）。
- **后果**：uid 前台计数永久 +1 → 该 uid 任务永久 HIGH（超时 600s 兜底，方向为过管控）。
- **修复方向**：observer 对 TERMINATED/END 按 foreground=false 处理（或启动时对账）。若不修，需在 spec R-7 级联一条"已知限制"。

### F-04（P3）ressched 监听注册结果不可判定
- **证据**【代码】：`res_sched_client.h:111` `RegisterSystemloadNotifier` 返回 void；`system_load_provider.cpp` 仅按 client 创建成功置 `registered_=true`。
- **后果**：注册静默失败时 `load listener [registered]` 误报；正确性有兜底（load=-1→MEDIUM），仅观测失真。

### F-05（P3）design 措辞与实现维度不一致
- design 写"调用方**进程**存在前台 Ability"，实现按 **uid**（应用维度）计数。spec 意图为应用前台状态，实现正确，design 表述需修正（P3 文档项）。

### F-06（P3）进程退出路径静态析构顺序【此处为推测】
- `ResschedSystemLoadProvider` 析构调 `ResSchedClient::GetInstance()`；若 so 卸载早于 ressched 库静态析构可能崩溃。AppMS 为常驻 SA，实际触发概率极低；建议观察项。

### F-07（P3）DumpPsched 忽略多余参数
- `--psched xxx` 静默接受；与 `--task` 对未知子命令报错的行为不一致。建议对齐报错。

### F-08（P3）创建者死亡的 schedule 清理无显式断言
- 路径已覆盖（`FinishTasksByCreatorInner` 经 `FinishTaskInner` 统一清理，证据 task_manager_service.cpp FinishTasksByCreatorInner→FinishTaskInner），但无测试断言 schedule 侧清空；建议随 F-02 一并补。
