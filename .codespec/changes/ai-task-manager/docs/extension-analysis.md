# 扩展场景分析：AI 任务管理机制的能力外溢（二期规划输入）

> 状态：分析文档（非交付承诺）· 生成：2026-08-26 第十三轮 · 依据：design.md（A-2 通用能力抽象）、proposal.md K-9（google-adk 概念映射）
> 定位：回答"本机制还能解决什么痛点"。分层标准：A 层=零设计增量（机制现状即可承载）；B 层=一次设计增量（在既有抽象上补一个机制点）；C 层=远期跟踪（架构方向性，需单独立项评估）。

## 0. 机制的可复用资产盘点

本机制交付后，系统获得三类**与"AI 任务"业务语义解耦**的通用资产（ADR-1/A-2 抽象化的直接产物）：

| 资产 | 位置 | 通用性说明 |
|------|------|-----------|
| 进程组调度原语 | `process_schedule`（design §5.1） | 进程组注册/注销、档位合并（max）、管控动作施加/撤销、死亡自动清理、结束恢复——不感知任务语义 |
| 资源管控出口 | `ResourceControlProxy`（design §6.4） | ControlAction 语义接口 + ControlRequest 完整上下文（taskId/type/priority/state/bundleName…），天然可对接多管控方（RSS/qos/温控/低内存查杀） |
| 挂起-回传交互通道 | `SubmitTaskInput` + `OnTaskNotice`（design §5.5） | 状态回调 + 通知类事件 + 白名单传递通道，任意"服务进程 ↔ 系统 UI"交互可复用 |

## A 层：零设计增量（机制现状即可承载，仅缺调用方）

### A-1 系统级长时任务通用化

- **痛点**：非 AI 场景的系统应用长时后台工作（批量索引、日志归档、媒体库扫描）同样受 RSS 冻结管控，现状只能各自申请 continuous task，粒度粗、策略散。
- **承载方式**：`process_schedule` 本就设计为通用"App 进程调度管理"能力（design §5.1 注记、ADR-1）。系统应用经 ITaskManager 创建任务（TaskType=DATA_PROCESSING/SYNC_TRANSFER）即获得同等档位管控，无需任何机制改动。
- **边界**：调用方须为系统应用（一期鉴权边界即如此）；三方应用开放需评估防滥用模型（R-2/R-21/R-22 上限体系已具备骨架）。
- **建议**：二期以此为首个推广场景，验证 A-2 抽象的真实通用性。

### A-2 A2A 多 Agent 编排的资源保障

- **痛点**：多 Agent 协作（supervisor→sub-agent 链）跨进程执行长流程，链上任意一环被冻结即整体停摆。
- **承载方式**：A2A 链路已天然覆盖（design §5.4.1 场景 9：A2A 经 agentmgr→AMS ConnectAbilityWithExtensionType，taskId 由 supervisor 参数透传）；B-2 链式信任（任务内进程可再纳管新进程，§5.3.1 ③）与 ADK supervisor→sub-agent 可信链一一对应；单任务纳管进程上限（16 可配）即编排链深度/宽度约束。
- **边界**：链上进程须显式携带 taskId（协作式透传，非自动继承）——与 ADK A2A "supervisor 提取状态参数透传"语义一致，无需改动。

### A-3 TaskType 驱动的差异化管控

- **痛点**：不同业务形态对资源的需求画像不同（下载类不在乎 CPU 峰值、播报类在乎唤醒延迟），单一"优先级"维度表达力不足。
- **承载方式**：ControlRequest 已暴露 taskType（design §6.4"暴露更多信息的意图"第①条），RSS 对接实现可直接按 type 定制策略（如 DOWNLOAD 类豁免冻结但不提权、VOICE_PLAYBACK 类优先保障唤醒延迟），本模块上层零改动。

## B 层：一次设计增量（在既有抽象上补一个机制点）

### B-1 任务资源画像与 Cost Limits 动态配额

- **ADK 对照**：Cost limits（max_llm_calls 防无限循环）→ 本机制已有静态上限（任务数/进程数/时长/续期）；缺**动态配额**——按创建者历史行为画像调整其上限（信任积累/惩罚降级）。
- **增量点**：process_schedule_policy 增加按 creatorTokenId 的配额计算（输入=既有 TASK_* hisysevent 序列，输出=该创建者各项上限），策略层单点改动，无接口变更。
- **价值**：防滥用从"一刀切上限"进化为"分级信任"，为三方开放铺路。

### B-2 交互态智能降档

- **现状**：design §6.1 已列二期开放项——HIGH/CRITICAL 任务进入交互态后自动降为限时豁免档（交互等待=低活动、需快速唤醒，与 MEDIUM 语义接近），压缩用户无响应期间的资源占用。
- **增量点**："状态×档位"二维映射表（process_schedule_policy），约一处策略改动；需与交互超时（F-5 两段式处置）联动设计降档后的恢复路径。
- **前置**：真机验证交互态期间高档豁免的实际资源占用数据，收益明确再启动。

### B-3 多 AI 应用资源仲裁

- **痛点**：多款 AI 助手（或多 Agent 框架）并发创建高优任务时，系统需要仲裁而非先到先得。
- **承载方式**：档位合并（max）+ 全局豁免进程上限（64）+ 创建者任务上限（16）**已是仲裁原语**——冲突时后到者被 R-22 拒绝并告警。
- **增量点**：仲裁策略从"上限拒绝"升级为"抢占/协商"（低价值 HIGH 任务让位给 CRITICAL），需任务价值度量输入（依赖 B-1 画像）与抢占时序设计（豁免撤销→重算→通知创建者）。接口无变更，OnTaskNotice 扩事件类型即可。

### B-4 资源压力预警（RESOURCE_PRESSURE 类通知）

- **痛点**：创建者对系统资源紧张无感知，任务失败后才知（事后 TASK_ABUSE_WARNING）。
- **增量点**：OnTaskNotice 扩展 RESOURCE_PRESSURE 事件类型（低内存/温控/冻结策略收紧时，RSS 经 RCP 上行通知 → task_mgr 派发给相关任务创建者），创建者可主动降档/暂停，从"被动拒绝"变"主动避让"。依赖 RSS 对接（O-3）时一并评估上行通道。

## C 层：远期跟踪（架构方向性，需单独立项）

| 方向 | 意义 | 关键依赖 |
|------|------|---------|
| 以任务为中心的调度观 | 任务（而非进程）成为资源调度的第一公民：RSS 策略直接按任务画像调度，进程只是任务载体 | RSS 侧架构演进；本机制已提供 ControlRequest 上下文作为输入 |
| 跨设备任务迁移 | 任务及其资源保障随分布式流转跨设备迁移（taskId 全局化、管控状态随迁） | 分布式软总线任务接续（mission 流转）+ 分布式 RSS 策略对齐 |
| 分布式远端进程纳管 | 任务进程分布多设备时，本端任务管理需纳管远端进程并施加远端管控 | 分布式进程视图（远端 pid 映射）+ 远端 RSS 接口 |

## 边界：三不碰（延续 proposal"明确不包含"）

1. **安全管控**：任务机制不做权限/隐私策略裁决（仅基础鉴权 + B-2 身份校验）；安全细则归安全子体系。
2. **定时调度本身**：定时触发归调用方（WorkScheduler/闹钟等），本模块只管任务执行期管控——避免与既有调度体系职责重叠。
3. **任务内容语义理解**：payload 对本模块是不透明字符串（仅做大小/权限管控），不理解、不解析业务语义——保持层间解耦。

## 优先级建议（供二期规划参考）

1. **B-2 交互态智能降档**（设计已预留、增量最小、真机数据可得）
2. **A-1 系统级长时任务通用化**（零增量推广，验证抽象通用性）
3. **B-4 资源压力预警**（随 RSS 对接 O-3 一并评估，联调成本低）
4. **B-1 动态配额 / B-3 多应用仲裁**（互为前置，构成"分级信任+抢占"完整故事，需产品定义）
5. C 层随架构演进跟踪，不进二期排期。
