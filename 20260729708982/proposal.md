# Proposal


## 1. 背景与问题（Why）

PC设备支持双模式运行（PC模式/PAD模式），同一应用可能存在PC模式版本和PAD模式版本。两个版本的包名相同但功能不同、签名不同。

**当前问题**：现有的包管理接口（安装、更新、卸载、查询等）只能按包名区分，无法满足双模式场景下的精确操作需求。用户无法精确管理同名不同包应用，可能导致误操作、数据混淆或功能异常。

**解决思路**：通过在意图存储Key中增加AppIndex字段，区分不同模式的应用，实现完整的双模式生命周期管理。

## 3. 目标 / 非目标

### 目标

- 安装意图管理：支持按"包名+AppIndex"精确安装目标应用
- 更新意图管理：升级时按模式更新意图，删除同名同包意图
- 卸载意图管理：按"包名+AppIndex"精确删除对应模式应用
- 查询意图管理：默认返回当前模式+同名同包意图
- 执行意图管理：默认执行当前模式意图
- 脏数据清理：执行失败时清理同名同包数据

### 非目标

- 不涉及接口变更（仅内部实现调整）
- 不涉及UX/交互设计变更
- 不支持从非同名同包回退到同名同包
- 不回合OpenHarmony 7.0数据

## 8. 自有生态设备差异规格

不涉及。本需求为意图存储 Key 结构扩展，通过 AppIndex 字段区分2种模式（PC模式/PAD模式）下同名不同包应用，属于平台内部数据结构变更，与具体设备形态无关，不存在设备差异化规格。AppIndex 字段在所有设备形态上行为一致。

## 9. DFX设计

不涉及。本需求为平台内部 Key 结构变更，无可靠性、可测试性、可维护性专项设计要求：
- 可靠性：意图存储 Key 扩展 AppIndex 字段后，现有查询逻辑向后兼容，失败时清理脏数据机制保障数据一致性
- 可测试性：所有验证通过 UT 覆盖（SC-01~07 均有 UT 验证），无专项 DT 设计
- 可维护性：复用现有意图存储架构，仅 Key 结构扩展，无新增维护通道

## 11. 技术方案

### 核心设计

在现有意图存储Key上增加AppIndex字段，统一处理同名同包和同名不同包场景。

**Key结构变化**：
- 原有：userID + bundleName + moduleName + intentName + version
- 新增：userID + bundleName + moduleName + intentName + version + appIndex

### 实现要点

1. **安装意图管理**
   - 同名同包：Key结构不变，与原有逻辑一致
   - 同名不同包：Key增加appIndex字段

2. **查询意图管理**
   - 返回"同名同包意图+当前模式意图"的合集
   - 内部实现自动过滤当前模式

3. **执行意图管理**
   - 默认执行当前模式意图
   - 优先匹配当前模式应用

4. **脏数据清理**
   - 意图执行失败时向数据库查询
   - 删除同名同包数据
