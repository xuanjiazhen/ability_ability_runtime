# Refuter 质疑规则与判定标准

> 本文件是 orchestrator Refute 环节（双模架构下作用于 Mode A 假设与 B→A 升格项）的详细规则。
> 原则：**只质疑，不发现**——refuter 不能新增任何 scanner 未报告的发现。质疑必须有代码证据。

## 0. 证据等级（双模架构新增，两轮试点实证）

推翻/降级所用证据分四级，**低级证据不得推翻高级结论**：

| 级 | 证据类型 | 可推翻 |
|---|---|---|
| E1 | 仓内代码阅读（上游守卫/常量来源/不可达分支） | Unverified 假设 |
| E2 | 部署面门禁（systemapi 标注/权限门控/模式开关唯一设置点/自攻自身无增益） | Unverified、Reasoned |
| E3 | 跨仓源码证据（拉仓追到调用点/设置点/净化点 file:line） | Reasoned |
| E4 | 执行级证据（harness/UT 复现或证伪运行） | 一切，含 Reproduced |

- **Reproduced 项不可被 E1-E3 推翻**（试点教训：仓内推理两次给出错误的机制描述）。
- 降级 P1→P2 至少需 E2+E3 组合；推翻 P1 至少需 E3（"确认不可达/防护成立"的跨仓 file:line）。
- 廉价分诊前置：E1/E2 级质疑在 Mode A S3 完成，refute 环节聚焦 E3/E4。

## 1. 审查范围

> 前三层（§2.1–§2.3）只降不升，是历史缺陷——系统性严重度通缩。自本版起新增第四层升级复审（§2.4），refute 变为**双向**：既质疑"不该报"，也质疑"被低估"。

| 优先级 | 审查策略 |
|--------|---------|
| P0（致命） | **全量审查**。推翻需要 E3/E4 级"确认不可达"证据，不允许仅凭"极难触发"推翻 |
| P1（严重） | **全量审查**。推翻需要 E3 级"上游有可靠防护/部署面不可达"证据（E1 仓内阅读不够） |
| P2（一般） | **抽样审查**（30% 或至少 5 条），优先审"可触发性存疑"的发现 |
| P3（提示） | 不进入 refute；Mode B hygiene 项按 static-checklist 抽检 10% |
| **P2/P3 @ T1 或 crown-jewel** | **全量升级复审**（§2.4）：凡 base=P2/P3 且发现点经 [`conventions.md`](../conventions.md) §7.5 判定为 T1 可达，或触及 crown-jewel 资产的发现，必须经第四层"被低估了吗"复审，不得跳过 |

## 2. 四层质疑

### 2.1 第一层：触发路径证伪 —— "真的能被触发吗？"

对每个 scanner 发现，从发现点往上追溯调用链。

| 质疑点 | 检查方法 | 推翻/降级标准 |
|--------|---------|--------------|
| 上游空指针防护 | 追溯发现点函数的调用者，检查传入参数前是否有 `if (ptr == nullptr) return` | 上游有可靠防护 → 推翻 |
| 不可达路径 | 检查发现点是否在 `#ifdef DEBUG`、已废弃函数、仅测试代码路径 | 确认不可达 → 推翻 |
| 数据来源为常量 | 标注为"外部输入"的变量，上游是否为 `static const` 或编译期已知值 | 确认常量 → 推翻 |
| IPC 接口暴露面 | 检查 IPC 接口的调用方权限（是否仅系统进程可调、是否有 SELinux 策略保护） | 仅系统进程可调 + 调用方可信 → 降级 |
| 断言/protobuf 防护 | 上游有 `assert(ptr != nullptr)` 或 protobuf 解析自带边界校验 | assert 不可靠（release 不生效）→ 维持；protobuf 可靠 → 推翻 |
| 弱防护 | 上游有检查但不完整（如仅检查了 nullptr 但没检查空字符串、仅检查了长度上限但没检查下限） | 降一级 |

**推翻 vs 降级**：
- 推翻 = 该发现从最终报告中移除（仍保留在 refute_log.md 中）
- 降级 = 该发现保留在报告中，严重等级下调（如 P0→P1、P1→P2）

### 2.2 第二层：影响夸大证伪 —— "后果真的这么严重吗？"

| 误报模式 | 常见案例 | 复审方法 | 判定 |
|---------|---------|---------|------|
| Defensive double-free | `free(ptr); ptr = nullptr;` 再 free | 检查两次 free 之间 ptr 是否被置 null | 有置 null → **推翻** |
| 进程退出时资源泄漏 | 静态分配的资源在进程退出时未释放 | 检查泄漏点是否在 exit() 路径上 | OS 自动回收 → **降级为 P3** |
| 整数溢出不可达 | scanner 标注 `int a = b + c` 溢出，但 b 和 c 均来自 `uint8_t` | 计算实际输入范围 | 不可溢出 → **推翻** |
| UAF 仅涉及日志打印 | "释放后使用"仅在 `HILOG_INFO` 中读整数值 | 检查 use 点是否影响控制流或数据完整性 | 仅日志 → **降两级** |
| 回调泄漏但回调数量有限 | scanner 标注"回调未清理导致泄漏"，但回调总数有上限（如最多 3 个） | 计算实际泄漏上限 | 上限小 → **降级** |
| 静态 bool 标志位无锁 | 标志位用于一次性初始化，设置了就不再改变 | 检查标志位是否只在单线程初始化阶段设置 | 单次设置 → **降级为 P3** |

### 2.3 第三层：跨 scanner 根因去重 —— "这两个发现本质是同一个根因吗？"

不同于 `file:line` 机械去重，基于修复方案反推。

**判定流程**：

1. **同一修复改动**：如果两个发现的修复方案是同一处改代码 → 合并
   - 例：SEC-005（空指针）+ LOG-004（状态更新异常）+ SEC-007（异常路径未释放锁）→ 根因是 `mission_list_manager.cpp:412` 缺一次 nullptr 检查，合并为一条

2. **连锁影响**：如果发现 B 是发现 A 的直接后果 → 合并到根因
   - 例：缺少边界校验 → 导致越界写入 → 导致相邻内存损坏 → 合并为一条"缺少边界校验"

3. **独立发现**：即使出现在同一文件，如果修复需要改动不同代码位置 → 维持独立
   - 例：同一文件的锁顺序问题和资源泄漏问题 → 维持两条

### 2.4 第四层：严重度低估复审 —— "是不是被低估了？"

> 与前三层对称的反向质疑。前三层问"真的该报吗/真的这么严重吗/是同一个根因吗"；本层问"**是不是被低估了**"。解决 scanner 系统性把 T1 可达缺陷压到 P2/P3 的通缩问题。

**审查范围**（与 §1 抽样不同，本层对以下发现**全量审查**，不得跳过）：

- 所有 base=P2/P3 且发现点经 [`conventions.md`](../conventions.md) §7.5 判定为 **T1 可达**的发现
- 所有触及 crown-jewel 资产（见 §7.5）的 P2/P3 发现
- 所有 base=P2/P3 但被 ≥2 个 pattern 同时命中的发现（组合风险信号）

**质疑点**：

| 质疑点 | 检查方法 | 升级标准 |
|--------|---------|---------|
| 后果低估 | 发现标注"功能失败/可恢复"，但实际触及进程稳定性/数据完整性/安全边界 | 后果触及崩溃/数据损坏/权限边界 → 升 P1 |
| 可触发性低估 | 标注"需组合条件"，但组合条件在正常运行路径上即可满足 | 正常路径可触发 → 升 1 级 |
| tier 未应用 | scanner 漏标 tier，发现点实际是 T1 但按 T3 定级 | 补标 T1 + 按 §7.5 升级 |
| 组合放大 | 单条 base 低，但与另一发现构成因果链（输入缺口 + 内存安全 / 校验缺失 + 越界） | 成链 → 按 §2.5 合并并升至链的后果等级 |

**升级上限**：单次升 1 级（P3→P2 或 P2→P1）；**组合成链例外**，可升至 P0（需引用链上每条发现的 file:line）。crown-jewel 加成叠加封顶 P0。

**判定**：
- ⬆️ 升级 = 该发现严重等级上调（如 P2→P1），保留在报告中，标注升级理由 + tier/链证据
- 与前三层证伪对称：**升级必须有代码证据**，不得凭"感觉严重"升级；必须引用具体 file:line 说明后果/可达性被低估的依据

### 2.5 漏洞链组合（升级特例）

当第四层判定 ≥2 条发现构成**因果链**（source gap → 中间缺陷 → 高后果 sink），合并为**一条**发现，等级取链上最高后果：

- 例：INP-003（路径输入未 Canonicalize，base P2）+ MEM-002（memcpy 长度失控，base P2）→ 合并为一条 P0"外部路径 + 长度失控 → 堆越界 RCE"，引用两处 file:line
- 例：IPC-003（size 字段未校验负数，base P0）+ MEM-002（越界写）→ 链上最高后果已是 P0，合并为一条，避免重复扣分

**与 §2.3 根因去重的区别**：

| | §2.3 根因去重 | §2.5 漏洞链组合 |
|---|---|---|
| 关系 | 同一根因的多表现 | 多个弱缺陷协同放大 |
| 方向 | 降数量（合并为一条，等级不变） | 升严重度（合并为一条，等级上调） |
| 触发 | 修复方案是同一处改代码 | 修复需改多处，但缺陷互相成就 |

链组合的 verdict 记为 ⬆️ 升级（reason 标注"成链合并: <链上 ID 列表>"），合并后条目引用链上所有 file:line。

## 4. refute 的约束

- **只质疑，不发现**：refuter 不能新增任何 scanner 未报告的发现
- **质疑必须有代码证据**：推翻或降级必须引用具体 file:line
- **升级同样必须有代码证据**：升级（⬆️）必须引用具体 file:line 说明后果/可达性被低估的依据，不得凭"感觉严重"升级
- **升级对称于证伪**：第四层（§2.4）与前三层同等强制——T1/crown-jewel 的 P2/P3 不得跳过升级复审
- **成链升 P0 需全链证据**：§2.5 漏洞链组合升至 P0 时，必须引用链上每条发现的 file:line，并说明因果衔接
- **被推翻的发现保留在 refute_log.md**：不进入统一报告正文，在 refute_log.md 中列出被推翻的条目和理由，便于人工复核捞回
- **P0 推翻需更严格证据**：不能仅凭"极难触发"推翻 P0，必须是"确认不可达"（上游硬 guard 或编译器保证）
- **refute_log.md 与最终报告一并交付**
